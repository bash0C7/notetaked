# 収録プロセス分離設計（issue #15）

## 背景

現行の`notetaked serve`は単一プロセス内で「音声tap → Diarizer → Transcriber → Reconciler → ファイル出力・制御応答」を一続きに行っている。話者分離/文字起こしの処理が詰まったり、そのプロセス自体がクラッシュ/ハングした場合、未処理の音声はメモリ上にしか存在しないため復元不可能な形で失われる。「フリーズっぽいので終了する」という運用そのものが最もデータを失いやすい操作になっている。

## ゴール

- 音声取り込みを、それ以降の処理（話者分離・文字起こし・出力・制御・peer通信）から独立したプロセスに分離し、後段が詰まる/クラッシュ/ハングしても取り込みは影響を受けない
- 後段プロセスがハング/クラッシュしても、メニューバーappが検知して再起動し、消失を「ハング中〜再起動完了までの未処理区間」に限定する
- 実装・運用の複雑さを増やしすぎない: ファイル管理は最小限、専用ログ/イベントの追加も最小限

## 非ゴール

- 取り込みプロセス自体の冗長化・多重化（取り込みプロセスが死んだ間の音声消失は許容する。取り込みは最も軽量でクラッシュ確率が低い設計とすることでリスクを下げるに留める）
- 生音声の永続的な保存・アーカイブ化（tmp領域のバッファは「録音」ではなく「バッファリング」という既存方針を維持する）
- 話者分離・文字起こしをさらに別プロセスへ分ける3プロセス以上の構成（今回は取り込み/それ以外の2プロセス分割のみ）

## アーキテクチャ概要

`notetaked serve`を2プロセスに分割する。

- **`notetaked capture`（新設）**: マイク/システム音声のtapのみを担う軽量プロセス。書き込み以外の処理を持たない
- **`notetaked process`（既存ロジックを継承）**: 話者分離・文字起こし・Reconcile・ファイル出力・iPhone/Watch peer通信・メニューバーappとの制御チャンネルを担う
- **メニューバーapp（Notetake.app）**: 両プロセスを個別に子プロセスとして起動・監視し、ハング/クラッシュを検知したプロセスだけを再起動する

## データフロー・再開の仕組み

- `capture`はセッション開始時、`process`から指定されたtmpセッションディレクトリ（`NSTemporaryDirectory()`配下）に、streamごとの生PCMファイル（`mic.raw` / `system.raw`）を作成し、先頭にformat情報（sample rate等）を書いたのち追記し続ける。ローテーション・切り詰めは行わない。削除はOSのtmp管理に任せる
- `process`は同じファイルを`DispatchSource`のfile-change監視で末尾から継続的に読む（tail方式）。これが平常時の処理経路そのものであり、再起動後のリプレイも同じ経路を使い回す（別経路のsocket等は作らない）
- `process`はstreamごとに「どこまで消費したか」を示すcheckpoint（byte offset）を、同じtmpセッションディレクトリ内の小さなファイルへ、finalな発話が1件確定する（timed.jsonlへ書かれる）たびに書く
- `process`が再起動した場合、checkpointの位置からtailを再開する。checkpointと実際に確定済みのtimed.jsonlとの間にある「処理中だった数秒〜十数秒」の区間だけが再処理対象になり、それ以外の音声は消失しない

## 心拍（heartbeat）と復旧

- `capture` / `process`はセッションの有無によらず、固定間隔（5秒）ごとに、固定パスの心拍ファイル（`~/Library/Application Support/Notetake/state/capture.heartbeat` / `process.heartbeat`）へ現在時刻を上書きする。新規の構造化ログ/イベントは追加しない
- メニューバーappはこの2ファイルのmtimeを一定間隔でポーリングし、閾値（15秒 = 心拍間隔の3倍）を超えて更新が無ければハングとみなす
- 復旧は段階的に行う:
  1. **graceful**: `process`には既存の`quit`コマンドを送り、猶予（5秒）を与える。`capture`には`SIGTERM`を送り、同様に猶予を与える
  2. 猶予内に終了しなければ`SIGKILL`で強制終了し、再起動する
- クラッシュ検知（プロセス終了）は既存の`terminationHandler`相当の仕組みをそのまま両プロセスに適用する（60秒に複数回落ちる場合は自動再起動を抑止する既存ロジックも両プロセスに適用）
- `capture`自体がハング/クラッシュしている間の音声は取り込まれないため復旧不可能（許容する）。`process`はcheckpointから再開するため、ハング中に未処理だった分だけがrerun対象になる

## 制御チャンネルの分割

- start/stop/rotate等のセッション制御は引き続きメニューバーapp→`process`間のstdio NDJSON
- `process`はセッション開始時、そのセッション用のtmpディレクトリパスを決めて`capture`へ伝える。`capture`は既存と同じstdio NDJSON形式で、「このディレクトリで録り始めろ／止めろ」という最小限の制御だけを受け付ける常駐プロセスとする

## コンポーネント一覧

| コンポーネント | 役割 | 既存/新規 |
|---|---|---|
| `notetaked capture` | 音声tap→生PCMをtmpへ追記するのみ | 新規（既存の`CaptureStream`のtap部分を切り出す） |
| `notetaked process` | 話者分離・文字起こし・Reconcile・出力・peer通信・制御応答 | 既存`serve`ロジックを継承。入力元が生tapから`capture`が書くtmpファイルのtail読みに変わる |
| checkpoint | streamごとの消費済みbyte offset | 新規（tmpセッションディレクトリ内の小ファイル） |
| heartbeatファイル | 生存確認用の時刻上書きファイル | 新規（2ファイル、Application Support配下） |
| メニューバーapp supervisor | 2プロセスの起動・heartbeat監視・graceful/forced再起動 | 既存の単一daemon監視ロジックを2プロセス対応に拡張 |

## エラーハンドリング

- `capture`が書き込み中のtmpファイルが壊れる（途中で切れる等）ケースは、`process`のtail読みがformat境界を超えて読まないよう、書き込み単位（サンプル境界）でのみ消費する
- checkpointファイルの書き込み中にクラッシュした場合、直前に書かれた値を使う（部分書き込みを避けるため、一時ファイル→rename方式で書く）
- `process`再起動時、checkpointファイルが存在しない（初回起動等）場合はセッション開始時点から読む

## テスト方針

- ユニットテスト: checkpoint読み書き（一時ファイル→rename）、tailの再開位置計算、heartbeat閾値判定ロジックを純粋関数として切り出しテストする
- 実機/CLI統合テスト（`make verify`外、HANDOFF.mdに実機検証項目として記録）:
  - `process`を`kill -9`し、メニューバーappが自動再起動、checkpointから再開して欠落が最小限であることを確認
  - `capture`を`kill -9`し、`process`側が音声の途絶を検知できる（heartbeat経由でメニューバーappが再起動する）ことを確認
  - 長時間セッション（既存issue #9の知見を踏襲）でtmp領域の増加がOSの管理範囲内であることを確認

## 運用上の前提

- userはセッションを原則回しっぱなしにし、終了は例外的な手動操作とする運用を想定している。この設計はその運用を前提にした特別な考慮は不要で、既存の長時間安定性（issue #9で確認済みの約6.5時間連続運転）と今回の障害復旧の頑健性がそのまま活きる
